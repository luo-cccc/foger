## 三、第 13 集卡点全记录（重要发现）

### 3.1 初写失败：emotional-hook 确定性门禁
审计 1 条 critical：emotionalHook 不是"具体观众疑问句"。门禁规则（`episode-quality-gate.ts` L217）要求含 `?`/`？` 或"能否/是否/会不会"。**真阳性**，初稿钩子确实只是陈述句。

### 3.2 revise 回退策略缺陷（产品发现 #1）
- 第一次 `revise` 把钩子改成带"？交还是不交？"的疑问句并持久化，但 JSON 里落盘的版本丢了问号（md 投影有、JSON 没有）——**投影与 JSON 字段不一致**。
- 后续两次 `revise` 均 "kept original draft"：`before blocking=1 critical=1; after blocking=3 critical=0`——候选修掉了 critical 但多出 2 条 warning，择优逻辑按 blocking 总数排序把候选回退。**critical 减少但 warning 增多时无法收敛**，建议：critical 权重应显著高于 warning，或按"先 critical 数、再 blocking 数"字典序比较。

### 3.3 memo 自相矛盾（产品发现 #2，最有价值）
确定性 memo 承诺门禁（`episode-memo-commitments.ts`）报 critical：「当前任务：沈砚要让阿贵在不受威胁的情况下，自己选择交出方既明篡改规则的记录」缺少正文证据。查 plan memo 发现 **planner 自己打架**：
- 「当前任务」要求本集交出记录；
- 「不要做」第 1 条明确写"不要让阿贵在本集直接交出记录——他的倒戈必须发生在下一集开头"；
- 「当集兑现」也写"阿贵当场没有交出记录"。

writer 忠实执行了「不要做」，门禁忠实抓住了「当前任务」未落地——**门禁是真阳性，根因是 planner LLM 产出自相矛盾的 memo**。人工编辑按 memo 自身意图把「当前任务」改写为"让阿贵亲眼看见笔迹被当众使用、沈砚替他挡话、阿贵开始动摇"后，审计 PASSED。

### 3.4 deepseek-v4-flash 审稿输出解析失败（模型抖动）
独立 `audit` 连续 3 次报「审稿输出格式异常，无法解析为 JSON」critical（`continuity.ts` 回退路径，maxTokens 3072）。第 1–12 集与 revise 内部审稿均正常，疑与第 13 集审计 prompt 长度 + flash 模型输出稳定性有关。**建议**：解析失败应自动重试 1–2 次再记 critical，避免模型抖动变成阻断性噪音。

### 3.5 state-degraded 级联与修复路径（产品发现 #3）
第 13 集过审后 `write next` 报"state-degraded"；`review approve` 后出现更深的 **manifest/state 错位**（manifest=13，current_state=12，episode_summaries 缺第 13 行），且错误信息没有指向修复命令。实际可用的修复链是：
1. `write repair-state` —— 拒绝（该集已 approve，非 state-degraded 状态），**状态机覆盖不全**；
2. `write sync` —— 确定性重放被状态校验拒绝：memo/handoff 里的状态变更（H010 推进、"阿贵欠他一笔"等）属于推断、无文本支撑，**校验器真阳性，LLM 状态投影爱写前瞻性推断**；
3. `write sync --brief "<人工编辑简报>"` —— 用简报约束状态重放只写文本直接呈现的事实后**一次通过**，truth files 重建成功。

这条"简报引导的状态修复"路径是真实可用的，但没有任何错误信息引导用户找到它；且 approve 可以提前于 state 提交造成 manifest 错位，建议 approve 时校验 state 完整性。

## 四、完本门禁与伏笔对账（产品发现 #4）

第 20 集《十年》在叙事上完成了终局闭环（沈砚典当十年记忆填账本缺口、忘记自己有孩子、方既明典当出头发却不再记得），memo 台账也逐条写明 `（near_payoff → resolve）`。但 `series complete` 报 7 条未闭环：

- **根因**：planner 把 H002/H007/H008/H011/H013/H014 的终结转写在 `advance:` 段（描述里带"→ resolve"），而伏笔池更新器**只认 `resolve:` 段**才翻转 status。结果备注里记录了"→ resolve"、状态却仍 `progressing`。正确写在 `resolve:` 段的 H009/H010/H012 全部正常翻成 resolved。
- **处理**：人工将 6 条伏笔状态在 `story/state/hooks.json` 与 `pending_hooks.md` 同步改为 resolved（对账行为，非内容修改），复跑 `series complete` → **passed**。
- **建议**：台账解析器应识别 advance 描述中的"→ resolve"终态标记，或在审计阶段对"advance 段出现 resolve 字样"给 warning 引导 planner 写对位置。
- 另有 D001（账本烧痕）一条 warning 级未闭环，属叙事上真实留白的支线，门禁合理放行（warning 不阻断完本）。

## 七、结论与改进建议优先级

**结论**：合并后的系统在真实付费模型上完成了 20 集端到端生产，20/20 过审、完本门禁通过。确定性门禁多次真阳性拦截（镜头数、钩子句式、memo 承诺、状态推断），没有发现误杀导致内容无法产出的情况。deepseek-v4-flash 可用但存在审稿 JSON 输出抖动。

**建议（按优先级）**：
1. revise 择优策略改为 critical 优先的字典序比较（3.2）；
2. 伏笔台账解析兼容 advance 段内的"→ resolve"终态标记，或审计期告警（四）；
3. 审稿 JSON 解析失败自动重试 N 次再记 critical（3.4）；
4. approve 前校验 state 完整性；state-degraded/manifest 错位错误信息中直接提示 `write repair-state` / `write sync --brief` 修复路径（3.5）；
5. planner memo 增加"当前任务 vs 不要做"自相矛盾的确定性自检（3.3）；
6. revise 持久化时校验 JSON 字段与 md 投影一致（3.2 丢问号问题）。
